# Django App Boundaries

Each app owns its models and domain rules. The goal is that each domain app can be installed and reused without requiring unrelated sibling apps. Cross-app integrations use explicit optional service/API contracts or narrowly scoped signals; do not duplicate authoritative state.

| App | Ownership | Principal integration boundary |
| --- | --- | --- |
| `users` | `CustomUser`, authentication integration, profiles/following/activity, MFA and notifications | Other apps reference `AUTH_USER_MODEL`; login delegates device policy to the Devices service contract. Users does not own device trust or registration state. |
| `core` | Shared settings/helpers, health endpoints, logging support, feature flags, cleanup command | Shared infrastructure only; cleanup imports the locally owned firmware/ad models for specifically bounded retention. |
| `ads` | Ad networks, units, campaigns, creatives, placements, events, affiliate data and settings | Consumers call ad services/routes; consent and provider credentials remain server-controlled. |
| `devices` | Operating-system (platform WebAuthn credential) and fallback browser-profile registrations, trust/revocation state, policy/configuration, device events, and legacy fingerprint analytics | Owns the OS credential public material and browser links, and the random first-party browser key (only its keyed digest is stored) used as the fallback. New registrations remain pending until an authenticated POST approves them (registering an OS credential approves it when the allowance has room); users cannot revoke registrations, while administrators can. One OS = one slot across browsers; an OS reinstall destroys the credential, but a website cannot detect the reinstall itself (see `device-slots.md`). Users authentication calls the app-owned service contract rather than copying device policy. |
| `blog` | Posts, categories, revisions/translations, feeds, public journal pages (listing, article, brand/model/chipset hubs, archives) and editorial behavior | Post status workflow (`blog.services.workflow`): owners or staff request review, staff with `blog.change_post` publish/schedule/archive; authors edit only their drafts, staff/editors edit live posts; scheduled posts are published by `blog.tasks.publish_due_scheduled_posts`. Bodies are sanitised on save and again at render (`blog.rendering`) to the CSP-compatible allow-list (no inline style, no iframes, same-origin images only). Authors are shown by public name only, automated posts by the editorial byline. Featured and paid posts are gated server-side (`Post.access`, `blog.paywall.resolve_gate`, `blog.access.can_set_premium_access`): a reader without access gets only a teaser through `public_excerpt`, never the body, and access for non-staff is decided by the optional shop contract in `blog.shop_gateway` (see `blog-featured-and-guides.md`); free posts are never withheld. The comments and ad-gate fields are not part of this app's page contract. `PostRevision` is the single content-history source. |
| `comments` | Comment state, automatic moderation, votes, reports and the staff moderation queue | Comments reference blog posts. New comments are screened by deterministic rules (`comments.services.moderation`): clean ones publish immediately, suspicious ones wait in the queue; repeated reader reports re-queue a published comment. Staff with `comments.change_comment` decide via `comments.services.decisions.moderate_comment`, which records reviewer, time and note in `moderation_flags`. Publishing notifies the post author and parent commenter once, after commit. |
| `firmwares` | Device/brand/chipset catalog, uploads and external submissions, firmware records, download tokens/sessions, gates, changelogs, guides and the automated brand/model/chipset blog posts | Pending uploads are approved or rejected by staff with `firmwares.change_pendingfirmware` (reviewer, time and reason stored on the record); only active, approved (`is_verified`) records are public everywhere (`firmwares.catalog`); files are stored locally or on an allowlisted external HTTPS host; the download gate (countdown, ad gate, single-use generic token, signed short-lived links) is locally owned; generated blog guides use the blog review service and never publish directly. |
| `tags` | Tag records, generic tagged-item relations, discovery, automation and curation | Blog associations. Catalog tags (brand, model, chipset, firmware category, post category) are created curated and attached automatically after commit (`tags.tasks.sync_post_tags`, idempotent). Keywords found in article text start as uncurated suggestions and are promoted automatically once three live posts mention them (`curate_suggested_tags`); staff can still approve, reject and merge (with confirmation) in the tag tools or admin. |
| `storage` | Where typed firmware bytes live: `FirmwareStorageLocation` rows keyed by ContentType + UUID, provider catalogue and verification | Local filesystem is the default and works end to end; external links reuse the firmware allow-list (`FIRMWARE_EXTERNAL_URL_ALLOWED_HOSTS`); Google Drive/S3 are disabled with a visible status page. Storage stores no credentials and never serves downloads — the firmware download gate does. |
| `seo` | `SEOSettings` (single settings authority), sitemap registry and `/sitemap*.xml` + `/robots.txt` routes, redirects, linkable entities | Sitemap sections come from the blog, firmwares, tags and pages apps; other apps read flags through `apps.seo.api`. The full SEO platform is a later phase. |
| `pages` | CMS pages (Markdown/HTML sanitised at render), scheduling, access levels, public widgets | Routes live under `/pages/`; widgets only list active, reviewed firmware via `apps.firmwares.catalog`. |
| `shop` | Package tiers, products, orders, packages, subscriptions, download quotas | Online payments, wallet and Stripe are not implemented (`ONLINE_PAYMENTS_ENABLED = False`); orders are requests that staff mark paid, which provisions packages exactly once. Quota helpers are an optional contract for the firmware download gate. |
| `marketplace` | Seller profiles, staff-reviewed verification, moderated listings | No checkout or payout; listings are visible only when approved, active and from a verified seller. |
| `wallet` | The central credits economy: `Wallet`, append-only `LedgerEntry`, admin-editable `RewardRule` (earn) and `CreditPrice` (spend), escrow holds, offline top-up requests, staff-reviewed payout requests, `WalletSettings` (conversion rate, limits) | Contract in `apps/wallet/api.py` (see `docs/04-backend/wallet-economy.md`): other apps declare `RewardEvent`/`SpendSink` in `reward_events.py`/`spend_sinks.py` and call `grant_reward`, `spend`, `refund`, `lock_escrow`, `balance`; they never keep their own balances or reward amounts. Credits are whole numbers in an internal currency; online payments stay disabled, so top-ups and payouts are confirmed by staff. |
| `referral` | Personal referral codes, invited-user links (`Referral`), referral anti-abuse settings | Captures `?ref=`/`/referral/r/<code>/` into the session, links the invitee at sign-up (allauth `user_signed_up`) and pays the referrer through the wallet event `referral.verified` only after the invitee verified their email and had a first contribution approved (`contribution.approved` event). One reward per invitee; self-referral, same-network and same-device (devices contract `users_share_device`, optional) are refused. |
| `consent` | `ConsentCategory`, versioned `ConsentPolicy`, append-only anonymised `ConsentDecision` (hashed IP/user agent, random visitor id, retention purge), the consent banner and the privacy centre (`/consent/`) | THE consent source. `apps.consent.services.has_consent(request, category) -> bool` (categories `necessary`, `analytics`, `advertising`; optional ones are opt-in and off after a policy version change or while the app is switched off). `ads` (advertising) and `site_settings` (GA/GTM loader and its CSP hosts, analytics) call it; nobody reads the consent cookie directly. The banner is a server-rendered include (`{% consent_banner %}` in `base.html`) with a small Alpine CSP component; the choice lives in one first-party `HttpOnly` cookie and can be withdrawn from the footer "Cookie settings" link. |
| `gamification` | `XPRule`, append-only `XPTransaction` (idempotent `key`), `Level`, `Badge`/`UserBadge`, `Streak`; leaderboard computed live | Subscribes to `firmware.approved` (uploader; fulfilled requests), `wallet.credited` (`referral.verified`, `bounty.fulfilled`), an approved-comment `post_save`, and the generic `gamification.award_xp` event. XP is the one reputation score (mirrored into `users.Reputation`). Badge credits are paid through `wallet.api.grant_reward("gamification.badge_earned")`. Public pages `/community/badges/`, `/leaderboard/`; `{% load gamification_tags %}{% user_badges user %}` for profile templates. |
| `bounty` | `Bounty` (credits escrowed on a firmware request, model or variant, linked by ContentType), `BountyClaim`, `BountyDispute` (staff queue), append-only `BountyLog` | Escrow and payouts only through `apps.wallet.api` (`lock_escrow`, `release_escrow`, `cancel_escrow`); paused honestly when the wallet is not installed or switched off. Subscribes to `firmware.approved` and settles bounties whose request, model or variant matches; refunds on cancel, expiry or the poster fulfilling their own bounty. `{% load bounty_tags %}{% bounty_cta "request" obj %}` is the optional "add a bounty" step for request pages. Public pages under `/bounty/`. |
| `distribution` | `Channel` (16 platform adapters; off by default; credentials encrypted), `Campaign` presets, `ShareJob` (unique idempotency key per channel, object and round), append-only `ShareLog`, `ShortLink`/`ClickEvent` (first-party `/go/<code>/`, no personal data), `MediaAsset`, `DistributionSettings` | Shares newly approved firmware pages (`firmware.approved`) and first-published human blog posts (`blog_post_published`) through plain HTTPS APIs via `apps.seo.fetcher` (SafeFetcher). Retry with backoff for transient failures, terminal failure for refusals, a channel that fails ten times in a row switches itself off, approval/schedule modes, A/B and evergreen automation, Pillow cards and ffmpeg video when available. No paid SDKs. See `distribution.md`. |
| `promotions` | `Promotion` (campaign: kind, audience, window, caps/budget, earn rules), idempotent `PromotionGrant`, `PromotionProgress`, append-only `PromotionLog`; offer pages under `/offers/` | Plugs into other apps only through their seams: shop `register_entitlement_modifier` (bonus quota/devices, package grants via `activate_package`), wallet `register_reward_modifier` and `credit`, `users` announcement gate/view hooks (banner + one notification), `ads.Campaign.promotion`, search provider `offer`. Never keeps balances or quotas; see `docs/04-backend/promotions.md`. |
| `site_settings` | `SiteSettings` singleton plus verification meta tags/files: site identity and branding, contact/social/share defaults, localization, maintenance mode, force-HTTPS, email credentials (encrypted), reCAPTCHA, verification-code shape, firmware download gate, analytics IDs | One cached accessor (`get_site_settings`, plus `get_email_runtime_config` and `get_recaptcha_secret` for secrets), a context processor and request middleware. It owns nothing that `users.UsersSettings`, `devices.DeviceConfig`, `seo.SEOSettings`, `core.AppRegistry`, blog, comments or ads own; the field-to-owner mapping is in `docs/04-backend/site-settings.md`. Other apps import only its `services` module. |

## Standalone-app status and rules

- Add a model to the app that owns its lifecycle, not to `core` for convenience.
- Keep API/UI authorization inside the owning app.
- Before adding a cross-app import, verify the target app is installed and the public contract exists.
- Test cross-app event effects, duplicate delivery, and failure semantics.
- Keep migration dependencies acyclic where possible and use app labels from `apps.py`.
- Cross-app imports must target only installed apps and documented contracts; do not restore obsolete integrations.
- There is no personal file storage (owner decision). "My files" at `/files/` belongs to `users` (`apps/users/library*.py`): it reads `firmwares.ServedDownload` and `shop.entitlements` through lazy imports and every re-download goes through the firmware download gate, never a direct file URL.
- The Devices registration contract is distinct from MFA, hardware fingerprinting, and download entitlements. Legacy `DeviceFingerprint` records are historical analytics and are not an alternate registration authority.
- Installed apps are connected in this project, but standalone installation has not yet been verified for all apps. Existing sibling imports and migration/model dependencies must be inventoried and removed or made optional before claiming the portability goal is complete.
- Dialogs follow "core = shell, app = content" (`docs/05-frontend/dialogs.md`): `core` owns only `components/dialog.html`, `apps/core/dialogs.py` (`DialogView`, `DialogForm`) and `dialogs.js`; every concrete dialog (`templates/<app>/dialogs/`, `apps/<app>/dialogs.py`) lives in the app that owns the behaviour, and `core` never imports a domain app for it. Browser-native `alert/confirm/prompt`, the HTMX confirm attribute and inline confirm handlers are forbidden (`tests/backend/test_no_native_dialogs.py`).
- Keep project-level tests in `tests/backend/` and `tests/frontend/`; integration tests spanning app ownership belong in `tests/backend/integrations/`.
- New direct sibling imports are prohibited unless documented as an explicit integration boundary with tests. Prefer app-owned optional adapters or caller-provided contracts over mandatory sibling imports.
