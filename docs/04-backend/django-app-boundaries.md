# Django App Boundaries

Each app owns its models and domain rules. The goal is that each domain app can be installed and reused without requiring unrelated sibling apps. Cross-app integrations use explicit optional service/API contracts or narrowly scoped signals; do not duplicate authoritative state.

| App | Ownership | Principal integration boundary |
| --- | --- | --- |
| `users` | `CustomUser`, authentication integration, profiles/following/activity, MFA and notifications | Other apps reference `AUTH_USER_MODEL`; login delegates device policy to the Devices service contract. Users does not own device trust or registration state. |
| `core` | Shared settings/helpers, health endpoints, logging support, feature flags, cleanup command | Shared infrastructure only; cleanup imports the locally owned firmware/ad models for specifically bounded retention. |
| `ads` | Ad networks, units, campaigns, creatives, placements, events, affiliate data and settings | Consumers call ad services/routes; consent and provider credentials remain server-controlled. |
| `devices` | Browser-profile registrations, trust/revocation state, policy/configuration, device events, and legacy fingerprint analytics | Owns the random first-party browser key and stores only its keyed digest. New registrations remain pending until an authenticated POST from that browser approves them; users cannot revoke registrations, while administrators can. The key recognizes a browser profile, not a physical machine or OS reinstall. Users authentication calls the app-owned service contract rather than copying device policy. |
| `blog` | Posts, categories, revisions/translations, feeds, public journal pages (listing, article, brand/model/chipset hubs, archives) and editorial behavior | Post status workflow (`blog.services.workflow`): owners or staff request review, staff with `blog.change_post` publish/schedule/archive; authors edit only their drafts, staff/editors edit live posts; scheduled posts are published by `blog.tasks.publish_due_scheduled_posts`. Bodies are sanitised on save and again at render (`blog.rendering`) to the CSP-compatible allow-list (no inline style, no iframes, same-origin images only). Authors are shown by public name only, automated posts by the editorial byline. The comments and ad-gate fields are not part of this app's page contract: article gating is not implemented and never withholds content. `PostRevision` is the single content-history source. |
| `comments` | Comment state, automatic moderation, votes, reports and the staff moderation queue | Comments reference blog posts. New comments are screened by deterministic rules (`comments.services.moderation`): clean ones publish immediately, suspicious ones wait in the queue; repeated reader reports re-queue a published comment. Staff with `comments.change_comment` decide via `comments.services.decisions.moderate_comment`, which records reviewer, time and note in `moderation_flags`. Publishing notifies the post author and parent commenter once, after commit. |
| `firmwares` | Device/brand/chipset catalog, uploads and external submissions, firmware records, download tokens/sessions, gates, changelogs, guides and the automated brand/model/chipset blog posts | Pending uploads are approved or rejected by staff with `firmwares.change_pendingfirmware` (reviewer, time and reason stored on the record); only active, approved (`is_verified`) records are public everywhere (`firmwares.catalog`); files are stored locally or on an allowlisted external HTTPS host; the download gate (countdown, ad gate, single-use generic token, signed short-lived links) is locally owned; generated blog guides use the blog review service and never publish directly. |
| `tags` | Tag records, generic tagged-item relations, discovery, automation and curation | Blog associations. Catalog tags (brand, model, chipset, firmware category, post category) are created curated and attached automatically after commit (`tags.tasks.sync_post_tags`, idempotent). Keywords found in article text start as uncurated suggestions and are promoted automatically once three live posts mention them (`curate_suggested_tags`); staff can still approve, reject and merge (with confirmation) in the tag tools or admin. |
| `storage` | Where typed firmware bytes live: `FirmwareStorageLocation` rows keyed by ContentType + UUID, provider catalogue and verification | Local filesystem is the default and works end to end; external links reuse the firmware allow-list (`FIRMWARE_EXTERNAL_URL_ALLOWED_HOSTS`); Google Drive/S3 are disabled with a visible status page. Storage stores no credentials and never serves downloads — the firmware download gate does. |
| `seo` | `SEOSettings` (single settings authority), sitemap registry and `/sitemap*.xml` + `/robots.txt` routes, redirects, linkable entities | Sitemap sections come from the blog, firmwares, tags and pages apps; other apps read flags through `apps.seo.api`. The full SEO platform is a later phase. |
| `pages` | CMS pages (Markdown/HTML sanitised at render), scheduling, access levels, public widgets | Routes live under `/pages/`; widgets only list active, reviewed firmware via `apps.firmwares.catalog`. |
| `shop` | Package tiers, products, orders, packages, subscriptions, download quotas | Online payments, wallet and Stripe are not implemented (`ONLINE_PAYMENTS_ENABLED = False`); orders are requests that staff mark paid, which provisions packages exactly once. Quota helpers are an optional contract for the firmware download gate. |
| `marketplace` | Seller profiles, staff-reviewed verification, moderated listings | No checkout or payout; listings are visible only when approved, active and from a verified seller. |
| `filemanager` | Per-user private files, folders, folder permissions, quotas, share links | Files live outside `MEDIA_ROOT`, are served only as attachments through authorised views, and are never exposed by the web server. |
| `site_settings` | `SiteSettings` singleton plus verification meta tags/files: site identity and branding, contact/social/share defaults, localization, maintenance mode, force-HTTPS, email credentials (encrypted), reCAPTCHA, verification-code shape, firmware download gate, analytics IDs | One cached accessor (`get_site_settings`, plus `get_email_runtime_config` and `get_recaptcha_secret` for secrets), a context processor and request middleware. It owns nothing that `users.UsersSettings`, `devices.DeviceConfig`, `seo.SEOSettings`, `core.AppRegistry`, blog, comments or ads own; the field-to-owner mapping is in `docs/04-backend/site-settings.md`. Other apps import only its `services` module. |

## Standalone-app status and rules

- Add a model to the app that owns its lifecycle, not to `core` for convenience.
- Keep API/UI authorization inside the owning app.
- Before adding a cross-app import, verify the target app is installed and the public contract exists.
- Test cross-app event effects, duplicate delivery, and failure semantics.
- Keep migration dependencies acyclic where possible and use app labels from `apps.py`.
- Cross-app imports must target only installed apps and documented contracts; do not restore obsolete integrations.
- The Devices registration contract is distinct from MFA, hardware fingerprinting, and download entitlements. Legacy `DeviceFingerprint` records are historical analytics and are not an alternate registration authority.
- Installed apps are connected in this project, but standalone installation has not yet been verified for all apps. Existing sibling imports and migration/model dependencies must be inventoried and removed or made optional before claiming the portability goal is complete.
- Keep project-level tests in `tests/backend/` and `tests/frontend/`; integration tests spanning app ownership belong in `tests/backend/integrations/`.
- New direct sibling imports are prohibited unless documented as an explicit integration boundary with tests. Prefer app-owned optional adapters or caller-provided contracts over mandatory sibling imports.
